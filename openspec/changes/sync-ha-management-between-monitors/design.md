## Context

当前主备管理链路中，`ha_manager` 插件只和本机房配置的江湖云监控通信：`report_state` 定时上报本机和 SSH 采集到的对端状态，`poll_monitor` 定时从江湖云监控拉取期望主机和切换任务。江湖云监控本地通过 SQLite 的 `ha_pair`、`ha_host_state`、`ha_switch_run`、`ha_switch_event`、`ha_alert_event` 等表保存主备关系、状态、切换任务、切换日志和异常事件。

现在部署形态是两个机房各自一套江湖云监控，每个机房通常只有本机房业务主机能稳定上报。当 A 机房业务主机停机时，A 江湖云监控仍可访问，但无法从 A 插件获得最新主备状态，也无法让 B 插件直接领取 A 江湖云监控上的切换任务。需要让 A/B 两套江湖云监控同步主备管理领域数据，使状态和任务能跨机房流转。

本设计不改变插件“只连接一个 `monitor_url`”的基本模型。插件仍然只向自己配置的江湖云监控上报和拉取任务；跨机房同步发生在两套江湖云监控之间。

## Goals / Non-Goals

**Goals:**

- 两套江湖云监控之间同步主备管理状态，使任一江湖云监控都能看到同一个 `pair_id` 下两台主机的较新状态。
- 支持在 A 江湖云监控创建切换任务后，同步到 B 江湖云监控，并由 B 侧可用插件通过 `poll_monitor` 领取执行。
- 同步切换执行日志、阶段 ack、最终状态和异常事件，使任务创建方江湖云监控也能看到完整执行过程。
- 对同一主备关系同一时间只允许一个有效切换任务，避免两个江湖云监控重复下发或两个插件重复执行。
- 保持服务器日报读取本地 `ha_*` 表的方式不变；同步完成后日报自然使用同步后的主备状态。

**Non-Goals:**

- 不直接同步 `/www/server/jh-monitor/data/default.db` SQLite 文件。
- 不要求主备管理插件同时配置或连接两套江湖云监控。
- 不引入外部数据库、消息队列或 NAS 文件同步作为第一版依赖。
- 不让江湖云监控直接 SSH 到业务主机执行切换脚本。
- 不解决两个机房网络完全互不可达时的实时一致性问题；网络恢复后允许补同步。

## Decisions

### 1. 使用通用业务事件同步，而不是同步 SQLite 文件

新增通用同步事件模型，例如 `ha_sync_event`、`ha_sync_cursor`、`ha_sync_applied` 和 `ha_sync_peer`。虽然表名前缀暂定为 `ha_sync_`，但它们不只服务主备同步，而是作为江湖云监控之间的通用事件同步底座。第一版只实现 `sync_type=ha_management`，用于同步主备关系变更、主机状态上报、切换任务创建/更新、切换日志追加、异常事件追加。

同步任务定时从对端江湖云监控拉取未应用事件，并按事件类型幂等写入本地 `ha_*` 表。

选择事件同步的原因：

- 可以明确表达“发生了什么”，并通过 `sync_type` 区分主备、主机等不同同步数据域。
- 可以通过 `event_id`、`source_monitor_id`、`object_key` 去重。
- 可以保留任务来源和执行归属，避免双边同时执行。
- 比直接复制 SQLite 文件更容易处理版本升级、字段兼容和冲突。

### 2. 设置页面使用“云监控同步”配置列表

每套江湖云监控仍然需要一个稳定的本机 `monitor_id`，用于判断事件来源、任务创建方和任务执行方。同步目标不使用单个固定 peer 配置，而是在江湖云监控设置页面新增“云监控同步”配置列表。列表支持添加、编辑、删除、启停和测试连接。

当前江湖云监控实例配置用于保存：

| 字段 | 说明 |
| --- | --- |
| `monitor_id` | 当前江湖云监控实例 ID，自动生成后保持稳定 |
| `monitor_name` | 当前江湖云监控名称，便于页面展示和日志排查 |

每条云监控同步配置用于保存：

| 字段 | 说明 |
| --- | --- |
| `sync_id` | 同步配置 ID |
| `sync_name` | 同步配置名称，便于识别对端机房或用途 |
| `sync_type` | 同步类型，第一版固定为 `ha_management`，表示同步主备相关数据 |
| `peer_monitor_url` | 对端江湖云监控地址 |
| `peer_monitor_id` | 对端江湖云监控实例 ID，首次握手后保存 |
| `peer_monitor_name` | 对端江湖云监控名称，首次握手后保存 |
| `sync_secret` | 当前同步配置使用的接口签名密钥 |
| `enabled` | 当前同步配置是否启用 |
| `last_sync_at` | 最近一次同步成功时间 |
| `last_error` | 最近一次同步失败原因 |

`monitor_id` 用于判断事件来源、任务创建方和任务执行方，不能使用 URL 或 IP 作为唯一身份。

同步配置列表中的核心配置项为“同步江湖云监控”和“同步类型”。这里的“同步类型”是为后续扩展其他同步数据域预留，不是在主备数据内部再拆分不同同步范围。

| 同步类型 | 说明 |
| --- | --- |
| `ha_management` | 同步主备相关数据；开启后主备关系、主机状态、切换任务、切换日志、异常事件都参与同步 |

### 3. 同步接口采用拉取模式和签名校验

两边江湖云监控都提供同步接口，例如：

| 接口 | 说明 |
| --- | --- |
| `/pub/ha_monitor_sync_handshake` | 校验同步密钥，交换 `monitor_id` 和基础能力版本 |
| `/pub/ha_monitor_sync_pull` | 按游标拉取对端新增同步事件 |
| `/pub/ha_monitor_sync_ack` | 确认本地已应用到对端哪个游标 |

同步任务由双方各自定时执行，遍历所有已启用的云监控同步配置，按每条配置和 `sync_type` 独立保存的 `last_event_id` 或自增游标拉取增量。接口需要复用或新增签名校验，至少校验 `timestamp`、`nonce`、`body_hash`、`signature`，避免伪造同步任务或重放事件。

选择拉取模式的原因：

- 两边只要能访问对端 HTTP 即可，不依赖长连接。
- 对端短暂不可达时，本地事件可以堆积，网络恢复后继续拉取。
- 和现有插件轮询模式一致，排查方式更简单。

### 4. 状态同步按“更新鲜 + 更可信”合并

`ha_host_state` 同步后按 `pair_id + host_id` 幂等写入。冲突处理规则：

| 情况 | 处理规则 |
| --- | --- |
| 新记录比本地 `last_report_at` 更新 | 覆盖本地状态 |
| 时间相同但来源可信度不同 | `collect_method=local` 优先于 `ssh_peer` |
| 对端同步过来的是失败占位 | 仅在本地没有更新鲜成功状态时保存 |
| 同一批双主机上报 | 保留 `report_batch_id`，让 `_normalizePair()` 继续按批次合并 |

这样 A 主机停机后，A 江湖云监控能通过 B 江湖云监控同步得到 B 插件上报的 `local` 状态，以及 B 通过 SSH 或失败占位采集到的 A 状态。

### 5. 切换任务必须有创建方和执行方

扩展 `ha_switch_run` 或关联元数据，记录：

| 字段 | 说明 |
| --- | --- |
| `origin_monitor_id` | 创建切换任务的江湖云监控 |
| `execution_monitor_id` | 允许向插件下发该任务的江湖云监控 |
| `claimed_by_host_id` | 领取任务的插件主机 |
| `claim_token` | 当前领取凭证 |
| `claim_expire_at` | 领取过期时间 |
| `sync_status` | 本地任务同步状态 |

当 A 江湖云监控创建任务但本地没有可执行插件时，应将 `execution_monitor_id` 指向 B 江湖云监控。B 同步到任务后，只有 B 江湖云监控的 `/pub/ha_pull_desired_state` 可以把 `execute_phase` 下发给 B 插件。A 江湖云监控即使保留该任务，也只展示状态和日志，不向本地插件下发执行。

### 6. 执行方选择遵循可执行性优先

创建切换任务时根据当前同步状态选择执行方：

```text
目标主机在当前江湖云监控有 local 上报
  => 当前江湖云监控可作为 execution_monitor

当前江湖云监控有另一台 local 主机，且该主机通过 ssh_peer 能触发目标主机
  => 当前江湖云监控可作为 execution_monitor

当前江湖云监控没有可执行主机，已启用同步主备相关数据，且对端江湖云监控有可执行主机
  => execution_monitor 指向对端江湖云监控

两边都不可执行
  => 任务不可创建或进入 waiting_executor，并提示原因
```

页面需要展示执行方选择结果，例如“任务将同步到 Mega 江湖云监控，由 Dev04B 插件执行”。

### 7. 同步任务不改变插件执行流程

插件仍然通过本机房江湖云监控的 `/pub/ha_pull_desired_state` 拉取任务，仍然使用现有 `local` / `ssh_peer` 方式执行阶段。跨江湖云监控同步只负责把 A 创建的任务变成 B 可下发的任务，并把 B 产生的日志和 ack 同步回 A。

### 8. 页面和日报以本地数据为准

江湖云监控页面继续读取本地 `ha_*` 表。同步事件应用后，本地表就是展示源。页面需要额外标识：

- 主备关系或主机状态是否来自对端同步。
- 切换任务由哪个江湖云监控创建。
- 切换任务由哪个江湖云监控负责执行。
- 最近同步时间和同步异常。

服务器日报不增加远程查询逻辑，继续读取本地 `ha_*` 表。同步启用后，两边日报自然包含同步后的主备状态。

## Risks / Trade-offs

- [Risk] 两边同时创建同一主备关系的切换任务。→ Mitigation: 以 `pair_id` 为粒度限制同一时间只有一个未完成任务；同步应用时发现冲突任务，后到任务进入 `conflict` 或 `waiting_retry`，页面提示人工处理。
- [Risk] 同步事件重复拉取或重复应用。→ Mitigation: 所有事件必须有全局唯一 `event_id`；日志事件继续使用 `switch_run_id + origin_host_id + seq` 幂等。
- [Risk] 两边时钟不一致影响状态新旧判断。→ Mitigation: 状态合并以插件上报的 `last_report_at` 为主，同时保存同步接收时间；明显异常时间只用于展示，不直接覆盖更新鲜状态。
- [Risk] A 创建任务后 B 未及时同步，用户以为没有执行。→ Mitigation: 页面展示同步状态、最近同步时间、执行方和未下发原因；同步失败写独立日志。
- [Risk] 同步密钥泄露导致伪造切换任务。→ Mitigation: 同步接口必须签名、校验 nonce、防重放；切换任务必须在页面和日志中显示来源江湖云监控。
- [Risk] 第一版只支持双江湖云监控，未来多机房扩展受限。→ Mitigation: 数据结构使用 `monitor_id` 和事件来源字段，接口先按一个 peer 实现，后续可扩展为多 peer。
