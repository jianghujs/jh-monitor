## Context

资源增长任务每隔数秒扫描一次，并通过 `host_alarm` 最新记录判断是否仍处于通知冷却期。当前数据库封装会把查询和写入异常返回为字符串，任务把查询异常视为“没有可用冷却记录”继续执行；写入结果也未校验。随后通知调用使用 `trigger_time=0`，导致数据库异常时每轮都可能发送邮件。

## Goals / Non-Goals

**Goals:**

- 冷却状态不可确认时采用保守策略，不发送重复通知。
- 只有告警记录成功写入后才发送通知。
- 通知层按主机和告警级别提供第二层冷却保护。
- 保持现有紧急和警告间隔配置语义不变。

**Non-Goals:**

- 不解决整个 SQLite 数据库的锁竞争问题。
- 不重构通用通知框架或资源增长预测算法。
- 不增加新的前端配置页面。

## Decisions

1. 将上一条告警查询结果分为“有效记录、无记录、查询失败”三种状态。查询失败时跳过该主机本轮分析和发送，因为无法证明冷却期已经结束。相比继续发送，这种策略可能暂时漏报，但不会形成邮件风暴。
2. 校验 `host_alarm.add()` 返回值。只有返回正整数记录 ID 时才进入通知发送；字符串错误、零值或其他异常结果均停止发送并打印错误。
3. 通知冷却键使用 `资源增长预警:<host_id>:<level>`，避免不同主机和不同级别共享同一把锁。`trigger_time` 使用当前最终告警对应的配置间隔。
4. 保留数据库告警记录作为主要冷却依据，文件通知锁作为故障兜底。这样无需迁移现有数据，也不改变告警历史展示。

## Risks / Trade-offs

- [数据库长期不可用时会暂时漏发增长预警] → 输出明确错误日志，并保留现有数据库告警历史作为恢复后的冷却依据。
- [通知锁文件损坏时兜底可能失效] → 数据库冷却仍是第一层保护；现有通知函数会重新初始化损坏的锁文件。
- [告警级别从警告升级为紧急时允许立即通知] → 冷却键包含级别，这是有意行为，确保升级告警不会被较低级别的冷却压制。
