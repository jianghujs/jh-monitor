## Context

日报链路为被采集主机的 rsyncd 检查工具 → report_collector → host-*-backup-* → report_analyser → 单机报告和概览 → report_sender。hostReportPipelineTask 仅负责调度。

当前 tool_check.py 的 _inspect_sync_task 在找到最新 run_* 日志后，对 realtime=true 提前返回。已有 _check_fixtime_sync_status 能识别删除比例超阈值、网络和权限错误等；fixtime_abnormal_tasks 已接入日报摘要。实时任务兜底入口 lsyncdRealtimeAllRun 同样生成 run_* 日志，但管道当前只收集标准输出。预检中止会打印原因，同时另存 preflight_* 日志。

当前分析器只取最新检查快照，任务明细仅遍历 send_open_fixtime_list。日报窗口默认从报告截止时间向前取 24 小时。插件默认计划模板为每 60 分钟执行兜底，用户环境可能为每日执行，因此本次不硬编码执行频率。

## Goals / Non-Goals

**Goals:**

- 实时任务独立呈现实时同步和定时兜底状态，兜底失败不被 lsyncd 正常掩盖。
- 保留日报窗口内已采集到的失败事件及其后续恢复信息。
- 复用现有日志规则、采集渠道、报告结构和发送机制，兼容升级期间的新旧数据。

**Non-Goals:**

- 不调整同步计划、删除保护阈值、rsync 23/24 退出码的既有容忍规则。
- 不实现未按计划执行、无日志即超时的告警，不回填升级前未采集的历史事件。
- 不新增实时通知渠道、独立数据库、同步调度器或远程自动升级功能。

## Decisions

### 1. 在插件端检查兜底运行日志

允许已启用实时任务进入运行日志检查，复用既有解析器；保留 send_open_realtime_list 与 send_open_fixtime_list 的任务分类，不把实时任务伪装成普通定时任务。旧字段继续表达当前最近一次结果；最新兜底失败进入 fixtime_abnormal_tasks，增加可选任务类型以便监控端标注“实时任务兜底”。

不能只删除提前返回：那只能修复最新状态，无法保留失败后恢复的记录。也不在监控端远程读取各主机日志，避免引入新访问链路。

兜底执行入口必要时补齐标准错误输出与明确的完成结果，使连接错误、预检中止、尚在运行和执行完成可区分。只调整日志证据，不改变实际同步命令、退出码容忍或计划。旧日志继续按现有内容规则解析，无法证明完成的活动日志不得直接标记成功；已知仍在运行的记录不作为终态失败。

### 2. 增量扩展检查结果，采集紧凑运行证据

在现有 result 下新增以下字段，保留既有字段类型：

| 字段 | 含义 |
| --- | --- |
| fallback_check_version | 新兜底检查契约版本，初始为整数 1 |
| fallback_checked_at | 本次插件检查时间，Unix 秒 |
| fallback_window_start / fallback_window_end | 本次日志扫描范围，Unix 秒，默认最近 24 小时 |
| fallback_scan_complete | 是否完整扫描目标范围；读取失败或主动截断时为 false |
| fallback_scan_reason | 扫描不完整原因，无异常时为空字符串 |
| fallback_runs | 已启用实时任务的运行结果数组 |

每个 fallback_runs 元素包含 task_name、log_file（文件名，不上传完整路径）、run_timestamp（运行开始时间）、observed_timestamp（观察时间）、status（success / failed / running / unknown）、reason。失败原因使用现有中文规则，优先保留明确的预检中止或 rsync 错误。时间优先从 run_YYYYMMDD_HHMMSS.log 文件名解析，旧命名回退文件修改时间；所有范围判断使用 Unix 秒。

按运行时间选取扫描范围内的日志，也纳入本次仍在更新、与扫描范围相交的日志，避免跨窗口长任务的结果丢失。额外保留最近一次历史运行用于当前状态展示，并明确其开始于窗口前、不计入窗口内次数。每次扫描读取紧凑结果而非上传完整日志，不将凭据、完整命令或传输文件清单放入新字段。同一次运行的 preflight_* 辅助日志不另算一次运行。单份日志读取上限为 8 MiB 字符，超过上限明确标记检查不完整。

collector 继续保存结构化 result，确认其不受 stdout 诊断文本截断影响。读取失败、超时或扫描不完整应显示检查证据不足，不能当作“全部正常”。现有 120 秒超时保护继续保留。

### 3. 日报合并窗口内的检查快照

保留最新快照用于实时状态、任务清单和版本识别；另外合并已查询到的 rsyncd 检查文档中的 fallback_runs，按 host_id + task_name + log_file 去重。同一运行多次被观察时采用最新 observed_timestamp，避免将运行中快照和完成结果算作两次运行。

最终按运行开始时间和现有报告窗口边界筛选；跨窗口开始的运行状态可展示为当前状态，但不得无说明计入“窗口内新发生次数”。只有窗口内失败之后的同任务成功运行才能标记恢复，其他任务成功或 lsyncd 状态正常不能作为恢复证据。

窗口内存在失败时始终保留异常摘要；若最后一次终态运行成功，标注“曾异常，已恢复”，否则标注“异常未恢复”。成功之后再次失败必须恢复为未恢复。运行中和未知状态不能证明恢复。已恢复事件仍进入 error_tips，使日报概览和单机异常发送保留当日事故提示。

采用所有窗口快照聚合，而非只取最新快照，可保留文件清理前已经采集到的证据。不新增历史日志拉取接口；采集停顿或文件被删除前从未采集的事件无法凭空恢复。

### 4. 日报展示与兼容

Rsyncd 区块分开显示“实时同步状态”和“实时任务兜底同步”，每个任务显示最近执行时间、结果、窗口内失败次数、原因和恢复情况。普通定时同步展示沿用原有逻辑。同一失败在旧异常列表和新运行证据同时出现时只输出一份摘要，新增文本统一 HTML 转义。

有失败时写入 error_tips 和 summary_tips，沿用主机异常标识、概览异常说明及单机异常报告发送条件。无需改变 task.py 调度或添加专门邮件发送分支。

缺少 fallback_check_version 的旧数据显示“未提供兜底检查，请更新插件”，使用提醒状态且不虚构运行正常或失败。新版完整扫描但无运行记录显示“窗口内无兜底运行记录”，不自动升级为故障；不完整扫描显示“检查不完整”及原因。最新配置已停用的任务不参加当前兜底健康判定。无实时任务的主机不增加无意义提示。

### 5. 保持 ES 数据与测试隔离

复用 host-*-backup-* 的 result 扩展对象和已有报告字段。源码中的备份映射允许动态字段，仍须只读核对目标环境的实际映射与字段类型；如需补充声明，仅做兼容新增，保留 host-report-* 历史结构。

验证使用模拟任务目录和日志、固定时钟、模拟采集结果与通知出口。重点验证超阈值、普通错误、失败后成功、重复采集、窗口边界、新旧数据、禁用任务及 HTML 转义。报告持久化验证使用既有脚本的测试索引选项，执行前确认目标主机和 ES 集群；真实通知不得作为测试副作用。

## Risks / Trade-offs

- [仅监控端升级无法恢复插件未采集的证据] → 明确跨仓库交付清单，先提供兼容监控端，再更新被采集主机插件。
- [最新日志仍在写入造成假异常] → 新日志提供执行完成证据，同一次运行后续观察覆盖早期状态；旧日志无法确认时显示未知。
- [大量日志或采集停顿导致扫描不完整] → 只读取范围内相关日志和紧凑结果，保留超时限制并显式展示不完整状态，禁止静默截断后报正常。
- [同名任务被删除后重建、时钟偏差影响关联] → 以主机、任务名和运行文件名关联，使用已有时间口径；任务稳定 ID 与跨主机校时不在本次范围。
- [已恢复仍收到异常日报] → 摘要明确标注已恢复，保留日报作为当日异常回顾的含义。

## Migration Plan

1. 在两个仓库分别完成检查工具、采集分析和针对性验证，记录需发布的文件。
2. 发布可兼容旧数据的监控端，确认报告渲染与测试索引持久化；需要重启时使用项目约定的 jhm 1 -y。
3. 更新被采集主机插件和必要的采集脚本，通过一次只读检查确认新契约已进入采集数据，等待正常采集后核对日报。
4. 不主动触发真实同步或通知，不迁移、重写历史报告。回滚时恢复对应代码；增量字段可保留，旧版本仍能消费既有字段。部署操作属于后续交付阶段。

## Open Questions

- 实施时核对部署版本的日志保留策略、完成标志和实际 ES 映射；这些影响兼容适配，不改变本提案的告警口径。
- 如后续需要“每天必须兜底一次”的缺失告警，另行定义计划来源、允许延迟和首次启用宽限期。
