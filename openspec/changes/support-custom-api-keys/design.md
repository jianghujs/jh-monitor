## Context

现有 api-keys.js 只提交名称、类型、权限、有效期等元信息。api_key_routes.py 将请求交给 ApiKeyStore.create，固定生成 jhm_ 加 64 位十六进制随机串；authenticate 固定校验 68 字符。api_key 表保存 SHA-256 摘要、前缀、AES-GCM 密文与 nonce，key_hash 有唯一索引。管理员查看原文使用部署本地的 data/api_key_master.key 解密。

## Goals / Non-Goals

**Goals:** 新增时自定义或粘贴已有密钥，使两个独立机房使用相同 Bearer 凭据；保留自动生成、原文取回、权限、停用、过期及现有密钥兼容。

**Non-Goals:** 不修改面板总密钥签名机制；不自动同步两个机房的权限或记录；不共享加密主密钥；不允许编辑已创建密钥的原文；不改江湖数据同步调用协议。

## Decisions

### 1. 创建时的可选 key 参数

POST /config/set_api_key 的 create 动作接收可选字段 key。缺省或空字符串仍自动生成；非空必须为字符串且完全符合 [A-Za-z0-9_-]{32,128}，大小写敏感，不去空格、不转换大小写、不自动添加前缀。只含空格属于错误而非自动生成。路由仅在 create 时传递此字段；update 收到非空 key 时明确拒绝，空值不改变原密钥，避免静默接受实际未修改的凭据。

选择沿用已有随机格式，而非改变随机生成算法；指定值通过同一创建管线计算摘要、加密、写入，避免两类密钥行为分叉。校验错误只描述规则，不回显提交值。

### 2. 表单与原文可见性

仅新增弹框在名称下方增加“密钥串（可选）”，默认空、密码输入，眼睛按钮切换显示/隐藏；说明“留空自动生成，可粘贴另一套云监控的调用密钥；32～128 位字母、数字、下划线或短横线”。沿用现有简洁布局，调整弹框高度或滚动，保证保存按钮可用。输入不使用会改变字节的 trim。前端校验与后端一致，后端为最终依据。

管理员/普通切换不清空输入。编辑不出现密钥输入，不自动请求原文；取消不提交，重新打开新增表单为空。列表维持脱敏、眼睛查看和复制行为，不在提示、URL、日志或浏览器持久化存储中写完整密钥。

### 3. 唯一性及存储

复用 key_hash 唯一索引，已停用或过期记录也占用其原文，重复时返回 ApiKeyError、HTTP 409，提示“该密钥已存在，请使用已有记录或填写其他密钥”。在 INSERT 的唯一冲突上确认是 key_hash 重复后转为业务错误，其余数据库错误沿用 503，不能把所有 IntegrityError 都伪装为重复。并发相同原文仅允许一条记录，不能覆盖已有类型、权限或有效期。

每个部署独立生成 key_id、nonce，使用各自的 AES-GCM 主密钥及 key_id/版本附加数据。相同原文在两边摘要相同但密文不同，均可独立解密。保留已有主密钥完整性校验，无 schema 迁移。

### 4. 鉴权兼容

将固定 68 字符校验改为与创建一致的格式验证；Bearer scheme 仍不区分大小写，密钥本身区分大小写。已有随机密钥满足新格式，不重算、重置或迁移历史记录。非法 Bearer 统一返回原有 401 消息，不暴露是否存在；合法格式仍需摘要命中、启用、有效期、权限和 API 总开关全部通过。

创建和认证复用同一纯格式判断，避免可保存但无法调用；前端另做等价校验。仅支持导入旧随机格式的方案不能满足任意自定义串，因此同步放宽长度范围。

### 5. 两个机房验收

使用两个临时 SQLite 库、各自不同的主密钥和两个独立 Flask 测试应用。A 创建或自动生成，B 指定同一原文。通过相同 Authorization 调用两边主备只读接口应均成功；两边可返回不同关系数据，证明请求独立。单边停用、过期、关闭 API 或取消 ha:read 后，仅该边被拒绝，不能跨部署修改另一边。验证两边查看原文一致、密文不同。

## Risks / Trade-offs

- [自定义字符串可能过于简单] → 保留默认随机生成及最短长度，说明优先复制已有自动生成密钥；不声称长度校验保证随机性。
- [同一密钥权限在两边不一致] → 配置说明要求两边分别检查权限、启用与有效期，测试验证独立性。
- [回滚旧鉴权仅支持 68 字符] → 回滚前将调用方切换为两边预先配置好的旧格式随机密钥；不删除现有记录。
- [导入已有值时无意覆盖凭据] → 重复创建返回 409，新增和编辑行为隔离。

## Migration Plan

无需 SQL、无需更新江湖数据同步。两个云监控发布前后端文件，重启面板进程并刷新浏览器。保留每台原有 data/default.db 与 data/api_key_master.key，升级不能重生成主密钥。先在 A 查看/创建密钥，再在 B 新增时粘贴，配置两边权限及总开关，分别验证接口，最后让调用方使用同一 token。测试只用隔离数据，不导出真实密钥或改动线上权限。

## Open Questions

无阻塞问题。本次仅新增时指定原文，后续如需原地轮换已有密钥，应单独设计调用方切换流程。
