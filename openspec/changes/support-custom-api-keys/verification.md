# 双机房自定义 API Key 部署与验收

## 升级

本次只更新云监控代码，不需要执行 SQL，也不需要修改江湖数据同步的调用协议。两套云监控都发布以下文件后，分别重启面板进程并刷新浏览器：

- `class/core/api_key_store.py`
- `class/core/api_key_routes.py`
- `route/static/app/api-keys.js`

重启命令：

```bash
/etc/init.d/jhm restart_panel
```

升级和备份时必须保留每台云监控自己的：

- `data/default.db`：保存该部署的调用密钥记录、权限、状态和有效期。
- `data/api_key_master.key`：解密该部署密钥原文的本地主密钥，权限必须保持 `0600`。

不要在两台机器之间复制或共用 `api_key_master.key`。两边使用相同 API Key 原文时，仍应由各自的主密钥、nonce 和 `key_id` 独立加密保存。

## 双机房配置

1. 在机房 A 的“设置 → API接口配置 → 调用密钥”中新增或查看准备给江湖数据同步使用的密钥。
2. 在机房 B 新增调用密钥，把 A 的密钥原文粘贴到“密钥串（可选）”。不要在编辑已有记录时修改原文。
3. 两边分别确认 API 总开关已开启、密钥已启用、有效期未过期。普通密钥需分别勾选 `ha:read`；管理员密钥沿用全部接口权限。
4. 使用同一个 Bearer token 分别请求两边固定接口 `/ha/api/local/relationships`。两边都应返回各自部署的主备关系快照。
5. 江湖数据同步只需在切换机房时更换云监控地址；Bearer token 可以保持不变。

两边的名称、权限、启用状态和有效期互不自动同步。修改或停用一边不会改变另一边。

## 隔离验收记录

自动化验收使用了两个临时 SQLite 数据库、两个独立的 AES-GCM 主密钥和两个独立 Flask 测试应用，没有读取或修改 `data/default.db`、线上密钥或线上权限。验收结果包括：

- 相同自定义原文可在两个部署各创建一条记录。
- 两边 `key_id`、nonce、密文和主密钥均不同，授权查看得到的原文一致。
- 同一个 Authorization 请求可以读取两边各自的关系数据。
- 任一侧关闭 API、停用、过期或取消 `ha:read` 后，仅该侧拒绝请求。
- 单个部署内重复或并发创建相同原文只保留一条记录，重复请求返回 HTTP 409。

## 回滚

如果回滚到只接受 68 位 `jhm_` 密钥的旧版本，应先在两套云监控中分别配置相同的旧格式密钥，再把调用方切换到该密钥，然后回滚代码。不要删除仍被调用方使用的密钥记录，也不要重建或覆盖 `data/api_key_master.key`。
