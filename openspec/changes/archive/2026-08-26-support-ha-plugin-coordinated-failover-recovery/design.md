## Context

当前普通主备切换已经朝“云监控下发任务、主备管理插件领取并执行”的方向演进。这个模型适合两台机器都可达的正常切换，但不能完整覆盖旧主停机、对端不可达、旧主恢复后需要补全为备机的故障场景。

本设计把故障切换和恢复闭环放在主备管理插件侧完成：云监控可以提供入口、展示状态和归档日志，但不作为恢复为备机的决策来源，也不直接 SSH 到机器执行脚本。插件之间通过已有绑定的 SSH/插件入口进行协调，存活插件负责判断可达性和执行能力。

## Goals / Non-Goals

**Goals:**

- 本地插件能连接对端插件时，支持从当前云监控或插件 UI 自由切换到任一主机。
- 本地插件无法连接对端时，只允许把本地存活机器切换为主，并进入降级运行状态。
- 降级运行时，插件侧记录不可达主机、当前主机角色和对端待切换标识。
- 故障服务器恢复后，由 `task.py` 周期触发主备管理插件执行恢复检查，插件读取对端角色和待切换标识，发现本机应切换为备用机时发送邮件通知，并自动执行或进入恢复保护流程。
- 云监控展示降级运行、待切换主机、恢复中和恢复完成状态，并展示插件上报日志。
- 所有执行方式、跳过阶段、恢复动作和失败原因在插件本地日志与云监控日志中可追踪。

**Non-Goals:**

- 不做完全自动故障切换；故障升主需要操作员确认。
- 不把两个云监控做成强一致集群或切换仲裁系统。
- 不让云监控直接 SSH 到江湖面板机器执行主备脚本。
- 不在对端不可达时允许切换到不可达主机。
- 不默认静默执行可能覆盖数据的旧主恢复；第一版允许配置自动恢复，未开启时自动进入恢复保护并等待人工确认。

## Decisions

### 1. 插件作为故障切换协调者

主备管理插件新增协调者角色 `coordinator_host_id`。发起切换时，当前可执行的本地插件先检查对端：SSH 是否可达、对端插件是否存在、对端插件配置是否完整、对端是否有切换锁、当前角色和自检状态是否可用于切换。

选择插件作为协调者，是因为 SSH 端口、密钥、对端插件路径、切换锁和脚本能力都在插件侧最准确。云监控只基于上报数据做判断会滞后，也缺少真实执行上下文。

### 2. 可达性决定执行模式

切换前插件输出执行模式：

| 执行模式 | 含义 |
|---|---|
| `full_switch` | 本地插件可连接对端，允许执行完整双边切换 |
| `local_failover` | 对端不可达，但目标是本机，允许跳过对端下线并本机升主 |
| `blocked_remote_unreachable` | 目标是不可达对端，拒绝执行 |

`full_switch` 中，协调者插件负责串联本地阶段和远程对端插件阶段。`local_failover` 中，协调者插件必须记录跳过对端下线的原因，并将主备关系标记为降级运行。

### 3. 降级状态由插件持久化

故障升主成功后，协调者插件写入本地状态文件，例如 `data/failover_state.json`。其中 `pending_switch_host_id` 和 `pending_switch_role` 是故障服务器恢复后用于补全流程的待切换标识：

```json
{
  "mode": "degraded_master",
  "current_master_host_id": "A",
  "pending_switch_host_id": "B",
  "pending_switch_role": "standby",
  "unreachable_host_id": "B",
  "coordinator_host_id": "A",
  "failover_run_id": "HSR_xxx",
  "failover_time": "2026-08-19 10:00:00",
  "pending_switch_required": true,
  "recovery_mode": "manual",
  "reason": "old_master_unreachable"
}
```

这个状态是恢复闭环的主要依据。云监控可以保存并展示同样字段，但不作为旧主恢复的唯一事实来源。

### 4. 旧主恢复后由 task 进程触发插件恢复判断

旧主恢复启动后，江湖面板 `task.py` 会按插件定时任务机制继续调用 `ha_manager` 的状态上报、云监控轮询或恢复检查入口。恢复判断不由 `task.py` 实现，`task.py` 只负责周期触发插件；插件读取本机状态、连接对端新主插件、获取对端协调状态，并判断本机当前角色是否与故障切换后的期望角色不匹配。

如果对端声明自己是当前主，且 `pending_switch_host_id` 是本机、`pending_switch_role=standby`，而本机仍处于主角色或主角色配置未清理，则本机先发送邮件通知并进入 `recovery_guard`，避免按旧主身份继续运行。若配置启用了自动恢复，插件可以直接执行 `recover_as_standby`；否则只进入恢复保护并提示人工确认。

恢复判断流程：

```text
task.py 周期触发 ha_manager
  |
  v
ha_manager 读取对端角色和待切换标识
  |
  v
发现本机是 pending_switch_host 且应切换为 standby
  |
  v
发送邮件通知
  |
  v
自动恢复开启：执行 recover_as_standby
自动恢复关闭：进入 recovery_guard 等待人工确认
```

### 5. 恢复为备机复用插件现有备机化能力

恢复动作为 `recover_as_standby`，由恢复机器自己的插件执行。它应复用现有下线、恢复配置、恢复插件配置、同步重建、自检等能力，而不是在云监控重新实现脚本。

恢复完成后，旧主插件上报 `role=standby`，新主插件清除 `pending_switch_host_id`、`pending_switch_role` 和 `pending_switch_required`，双方重新进入正常主备状态。为避免重复执行，恢复流程必须有本地锁和 `recover_as_standby` 执行状态记录。

### 6. 云监控只展示和归档

云监控接收插件上报的 `mode`、`execution_mode`、`pending_switch_required`、`pending_switch_host_id`、`pending_switch_role`、`recovery_status`、`degraded_reason` 等字段。列表和详情页展示当前是否降级、谁是当前主、谁待切换、执行方式和恢复日志。

云监控不下发 `recover_as_standby` 任务，也不作为恢复是否执行的裁决者。云监控可以提供入口跳转或提示操作员到插件页面确认恢复。

## Risks / Trade-offs

- [Risk] 旧主只是网络隔离但业务仍在写入，存活备机升主后可能双主。→ Mitigation: 故障升主必须人工确认，并在 UI 和日志中明确“对端不可达，已跳过下线，请确认旧主已停机或隔离”。
- [Risk] 旧主恢复时自动恢复为备机可能覆盖数据。→ Mitigation: 自动恢复必须有显式配置开关，并记录本机角色不匹配、对端主机确认、恢复配置和每个关键步骤；未开启时只进入恢复保护。
- [Risk] 两边插件状态不一致导致恢复判断错误。→ Mitigation: 恢复前必须验证对端当前主身份、failover_state、绑定关系和最近状态时间；验证失败时进入待人工处理。
- [Risk] 对端插件接口不可用但 SSH 可用。→ Mitigation: 允许通过 SSH 执行对端插件命令作为降级调用方式，但必须记录执行方式和失败原因。
- [Risk] 与现有云端两段式切换状态重叠。→ Mitigation: 本变更只扩展故障模式和插件间恢复闭环；普通可达切换仍复用现有预上线、正式上线流程。

## Migration Plan

1. 插件新增对端执行能力检查接口和插件间协调状态读取接口。
2. 插件切换前增加执行模式判断，区分完整双边切换、本地故障升主和目标不可达拒绝。
3. 插件故障升主成功后持久化降级状态，并上报云监控。
4. 插件定时任务中增加恢复检查入口，由 `task.py` 周期触发，发现本机匹配待切换标识且角色不匹配时自动执行或进入 `recovery_guard`。
5. 插件 UI 增加待切换为备机提示、恢复为备机确认入口和自动恢复配置。
6. 云监控后端兼容保存插件上报的降级和恢复字段，前端展示状态、提示和日志。
7. 通过可达、对端不可达、旧主恢复三类场景验证完整链路。

## Open Questions

- 自动恢复配置是否放在每个插件本地，还是主备关系配置中同时保存到两边插件。
- 恢复为备机是否默认执行增量恢复，还是根据插件已有预上线/恢复选项继承。
- `failover_state.json` 是否需要签名或版本号，防止旧状态误触发恢复。
- 旧主恢复后，如果检测到本机数据时间晚于新主，应如何提示人工确认数据处理策略。
