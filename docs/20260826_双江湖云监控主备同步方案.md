# 双江湖云监控主备管理数据同步方案

**更新日期**：2026-08-26  
**适用范围**：江湖云监控主备管理模块、江湖面板 `ha_manager` 主备管理插件  
**相关变更**：`openspec/changes/sync-ha-management-between-monitors`  

本文用于说明两个机房各自部署江湖云监控时，如何同步主备管理数据，并支持在一侧业务主机故障时，由另一侧江湖云监控和主备管理插件继续完成状态更新和切换执行。

---

## 1. 背景

当前部署形态是两个机房各自有一套江湖云监控，每个机房的业务主机通过江湖面板 `ha_manager` 插件上报主备状态。

现有链路中：

| 主体 | 当前行为 |
| --- | --- |
| 主备管理插件 | 只向本机房配置的 `monitor_url` 上报状态、拉取切换任务 |
| 江湖云监控 | 只保存本机收到的主备关系、主机状态、切换任务、切换日志 |
| 主备切换 | 江湖云监控创建任务，插件通过 `poll_monitor` 领取后执行 |

这会带来一个问题：如果 A 机房业务主机停机，A 机房江湖云监控还在，但无法继续从 A 插件获得主备最新状态，也无法让 B 机房插件直接领取 A 江湖云监控创建的切换任务。

需要补充两套江湖云监控之间的主备管理数据同步能力。

## 2. 目标

| 目标 | 说明 |
| --- | --- |
| 双端状态可见 | 任一机房江湖云监控都能看到同一个主备关系下两台主机的最新状态 |
| 跨监控切换 | 可以在 A 江湖云监控发起切换，由 B 江湖云监控下发给 B 插件执行 |
| 日志回传 | B 插件执行产生的切换日志、阶段结果和最终状态，需要同步回 A 江湖云监控 |
| 防重复执行 | 同一主备关系同一时间只能有一个有效切换任务，且只能由一个执行方领取 |

## 3. 同步方案对比

云监控同步数据方案对比：

- NAS 文件同步：
  - A 云监控写入 `NAS A` 的 `A目录`，配置同步任务同步到 `NAS B` 的 `A目录`。
  - B 云监控写入 `NAS B` 的 `B目录`，配置同步任务同步到 `NAS A` 的 `B目录`。
  - A 云监控读取 `NAS A` 的 `B目录` 中的同步数据，用来更新本地状态。
  - B 云监控读取 `NAS B` 的 `A目录` 中的同步数据，用来更新本地状态。
  - 适合场景：主要解决“两边状态可见”的问题，例如同步主备关系、主机状态、最近上报时间、异常摘要等状态快照。
  - 优点：
    - 不要求两套云监控直接互相开放 HTTP 接口。
    - 可以复用已有 NAS 同步任务，接入成本低。
    - 同步文件可直接查看，排查时比较直观。
    - HTTP 不通时，可以作为状态同步的兜底方式。
  - 风险：
    - 实时性依赖 NAS 同步周期，不适合秒级切换任务流转。
    - 写文件时需要用临时文件加 rename，避免对端读到未写完的数据。
    - 文件只解决传输问题，事件去重、版本比较、冲突处理仍然要在云监控里实现。
    - A目录、B目录如果配置反向或交叉，可能造成旧数据覆盖新数据。
    - 切换任务领取、执行日志、ack、领取过期等闭环状态，不适合只靠文件目录表达。
  - 建议定位：NAS 文件同步适合做“状态快照同步”或“离线兜底同步”，不建议让插件切换任务直接依赖文件目录领取。

- HTTP 事件同步：
  - A 云监控保存本地业务数据时，写入一条 `sync_type=ha_management` 的同步事件。
  - B 云监控通过 HTTP 接口按游标拉取 A 云监控新增的同步事件。
  - B 云监控成功应用事件后，推进本地同步游标，并记录已应用事件，避免重复应用。
  - B 云监控保存本地业务数据时，也写入同步事件。
  - A 云监控通过 HTTP 接口按游标拉取 B 云监控新增的同步事件。
  - A 云监控成功应用事件后，推进本地同步游标，并记录已应用事件。
  - 适合场景：主备关系、主机状态、切换任务、切换日志、异常事件都需要同步，且需要支持跨云监控切换执行。
  - 优点：
    - 同步的是业务事件，不依赖文件名或目录表达业务含义。
    - 可以按 `cursor`、`event_id`、`sync_type` 做增量同步，失败后便于重试。
    - 可以通过 `ha_sync_applied` 做幂等去重，避免重复写入和重复执行。
    - 切换任务、领取凭证、执行日志、阶段结果、最终 ack 都可以作为事件同步，任务闭环更完整。
    - 可以做同步密钥、签名、时间戳、nonce、body hash、防重放和同步类型校验。
    - 后续如果要同步主机数据、监控任务等其他数据，可以复用 `ha_sync_*` 通用同步底座。
  - 风险：
    - 需要新增同步配置、握手接口、拉取接口、游标、幂等应用和定时任务，开发成本更高。
    - 两套云监控之间需要能访问对端公开同步接口。
    - 签名、分页、重试、超时、错误记录需要设计完整。
    - 两边同时创建任务或状态乱序到达时，需要进入 `conflict` 或按规则合并。
  - 建议定位：HTTP 事件同步适合作为主方案，用来承载主备管理的完整业务闭环。

- 对比结论：
  - 如果目标只是“不丢失对端状态展示”，NAS 文件同步成本更低，可以作为状态快照方案。
  - 如果目标包含“跨云监控切换、执行日志回传、防重复领取、后续扩展”，HTTP 事件同步更合适。
  - 本文后续章节按 HTTP 事件同步展开，NAS 文件同步可作为离线兜底或只读状态快照方案保留。

## 4. 总体方案

采用“江湖云监控之间同步业务事件”的方式，不同步数据库文件。第一版只写入和应用 `sync_type=ha_management` 的主备相关事件，但 `ha_sync_*` 表按通用同步底座设计，后续可以继续承载主机数据、监控任务等其他同步类型。

```text
A 江湖云监控                         B 江湖云监控
┌──────────────┐                    ┌──────────────┐
│ ha_pair      │◀──── 事件同步 ────▶│ ha_pair      │
│ ha_host_state│◀──── 事件同步 ────▶│ ha_host_state│
│ ha_switch_run│◀──── 事件同步 ────▶│ ha_switch_run│
│ ha_switch_evt│◀──── 事件同步 ────▶│ ha_switch_evt│
│ ha_alert_evt │◀──── 事件同步 ────▶│ ha_alert_evt │
└──────┬───────┘                    └──────┬───────┘
       │                                    │
       │ report_state / poll_monitor        │ report_state / poll_monitor
       ▼                                    ▼
   A 主备插件                            B 主备插件
```

核心思路：

1. 江湖云监控保存本地收到的主备数据时，同时写入一条通用同步事件，事件的 `sync_type` 为 `ha_management`。
2. 对端江湖云监控定时拉取这些事件。
3. 拉取后按事件类型幂等应用到本地 `ha_*` 表。
4. 页面和日报仍然只读取本地 `ha_*` 表。
5. 切换任务通过 `origin_monitor_id` 和 `execution_monitor_id` 区分创建方和执行方，避免重复领取。

## 5. 数据同步范围

| 数据 | 现有表 | 同步用途 |
| --- | --- | --- |
| 主备关系 | `ha_pair` | 两边都能看到同一个 `pair_id`、关系名称、期望主机、实际主机、整体状态 |
| 主机状态 | `ha_host_state` | 同步本机和对端状态、自检结果、采集状态、最近上报时间 |
| 切换任务 | `ha_switch_run` | 同步预上线、正式上线任务、目标主机、阶段、状态、执行方 |
| 切换日志 | `ha_switch_event` | 同步插件执行过程日志，使任务创建方也能看到完整日志 |
| 异常事件 | `ha_alert_event` | 同步异常通知和恢复通知事件，便于两边展示一致 |

新增同步表建议。虽然表名前缀暂定为 `ha_sync_`，但这些表不只服务主备同步，而是作为江湖云监控之间的通用事件同步底座；第一版先承载主备管理数据。

| 表 | 说明 |
| --- | --- |
| `ha_sync_event` | 保存需要同步出去的通用业务事件，通过 `sync_type` 区分主备、主机等数据域 |
| `ha_sync_cursor` | 保存每条同步配置、每个同步类型已同步到哪个游标 |
| `ha_sync_applied` | 保存已应用的事件 ID 和同步类型，用于幂等去重 |
| `ha_sync_config` | 保存云监控同步配置列表，包括对端江湖云监控地址、名称、ID、同步类型、密钥、启停状态和最近同步结果 |
| `ha_sync_nonce` | 保存同步接口 nonce，防止签名请求被重复使用 |

## 6. 同步配置

每套江湖云监控需要有稳定身份，并在设置页面提供一个“云监控同步”配置列表。列表里的每条同步配置都可以独立设置“同步江湖云监控”和“同步类型”。这里的“同步类型”是为后续扩展其他同步数据域预留，例如未来可能同步主机数据；第一版只做“同步主备相关数据”。

建议在江湖云监控“设置”页面增加一个“云监控同步”配置列表：

| 列表能力 | 说明 |
| --- | --- |
| 添加同步 | 新增一条云监控同步配置 |
| 编辑同步 | 修改同步名称、同步江湖云监控、同步类型、同步密钥、启停状态等 |
| 删除同步 | 删除不再使用的同步配置，删除后不再拉取该配置对应的事件 |
| 启用/停用 | 单独控制某条同步配置是否参与定时同步 |
| 测试连接 | 和该配置对应的对端江湖云监控握手，校验地址、密钥和对端实例 ID |

每条同步配置建议包含：

| 页面配置 | 说明 |
| --- | --- |
| 同步名称 | 便于识别，例如 `同步 Mega 云监控主备数据` |
| 同步江湖云监控 | 对端江湖云监控地址，用于拉取对端同步事件 |
| 同步类型 | 第一版选择“同步主备相关数据”，后续可扩展为主机数据等其他同步类型 |
| 同步密钥 | 当前同步配置使用的接口签名共享密钥 |
| 是否启用 | 控制这条同步配置是否参与定时同步 |

同步类型第一版只支持一种：

| 同步类型 | 说明 | 适用场景 |
| --- | --- | --- |
| `ha_management` | 同步主备相关数据；开启后主备关系、主机状态、切换任务、切换日志、异常事件都会同步 | 两个机房江湖云监控之间共享主备状态，并支持跨江湖云监控切换任务流转 |

当前江湖云监控实例建议保存以下配置字段：

| 配置项 | 说明 |
| --- | --- |
| `monitor_id` | 当前江湖云监控实例 ID，自动生成后保持稳定 |
| `monitor_name` | 当前江湖云监控名称，例如 `Polaris 云监控`、`Mega 云监控` |

每条同步配置建议保存以下字段：

| 配置项 | 说明 |
| --- | --- |
| `sync_id` | 同步配置 ID |
| `sync_name` | 同步配置名称 |
| `peer_monitor_url` | 对端江湖云监控地址 |
| `peer_monitor_id` | 对端江湖云监控实例 ID，握手后保存 |
| `peer_monitor_name` | 对端江湖云监控名称，握手后保存 |
| `sync_secret` | 两套江湖云监控之间同步接口签名密钥 |
| `enabled` | 当前同步配置是否启用 |
| `sync_type` | 同步类型，第一版取值为 `ha_management` |
| `last_sync_at` | 最近一次同步成功时间 |
| `last_error` | 最近一次同步失败原因 |

`monitor_id` 用来判断事件来源、任务创建方和任务执行方，不能使用 URL 或 IP 替代。

## 7. 同步接口

江湖云监控之间使用 HTTP 拉取模式。两边都提供接口，两边也都运行同步任务。同步任务会遍历设置页面中已启用的“云监控同步”配置，分别按同步配置和同步类型读取各自游标，只拉取该配置对应 `sync_type` 的增量事件。

| 接口 | 说明 |
| --- | --- |
| `/pub/ha_monitor_sync_handshake` | 校验同步密钥，交换 `monitor_id`、名称和同步版本 |
| `/pub/ha_monitor_sync_pull` | 按游标拉取对端新增同步事件 |
| `/pub/ha_monitor_sync_ack` | 确认本地已成功应用到哪个游标 |

接口需要签名校验，建议沿用插件公开接口的思路：校验 `timestamp`、`nonce`、`body_hash`、`signature`，防止伪造请求和重放请求。

## 8. 状态同步流程

状态同步解决的是“一边主机故障后，另一边状态还能同步过来”的问题。

```text
B 主备插件 report_state
  │
  ├─ 上报 B local 状态
  ├─ 如果能 SSH 到 A，则上报 A ssh_peer 状态
  └─ 如果 A 不可达，则上报 A 采集失败占位状态
      │
      ▼
B 江湖云监控写入 ha_host_state / ha_pair
      │
      ▼
B 江湖云监控写入 sync_type=ha_management 的 ha_sync_event
      │
      ▼
A 江湖云监控定时拉取并应用事件
      │
      ▼
A 江湖云监控页面显示同步后的主备状态
```

主机状态合并规则：

| 情况 | 规则 |
| --- | --- |
| 同一个 `pair_id + host_id` 有多条状态 | 优先使用 `last_report_at` 更新的状态 |
| 时间相同但采集方式不同 | `collect_method=local` 优先于 `ssh_peer` |
| 同步过来的是失败占位 | 不覆盖本地更新鲜的成功状态 |
| 同一批上报包含两台主机 | 保留 `report_batch_id`，继续按现有展示逻辑合并 |

## 9. 跨江湖云监控切换流程

切换任务需要区分“在哪里创建”和“由哪里执行”。

| 字段 | 说明 |
| --- | --- |
| `origin_monitor_id` | 创建切换任务的江湖云监控 |
| `execution_monitor_id` | 允许下发任务给插件执行的江湖云监控 |
| `claimed_by_host_id` | 实际领取任务的主备插件主机 |
| `claim_token` | 领取凭证，避免重复 ack 或重复执行 |
| `claim_expire_at` | 领取过期时间 |
| `sync_status` | 当前任务同步状态 |

典型流程：

```text
A 业务主机停机
  │
  ▼
运维在 A 江湖云监控点击切换到 B
  │
  ▼
A 江湖云监控创建 ha_switch_run
  │
  ├─ origin_monitor_id = A
  └─ execution_monitor_id = B
      │
      ▼
任务事件同步到 B 江湖云监控
      │
      ▼
B 主备插件 poll_monitor 拉到任务
      │
      ▼
B 主备插件执行 local 或 ssh_peer 切换流程
      │
      ▼
B 江湖云监控收到日志和阶段结果
      │
      ▼
日志、ack、最终状态同步回 A 江湖云监控
```

执行方选择规则：

| 场景 | 执行方 |
| --- | --- |
| 当前江湖云监控有目标主机 `local` 上报 | 当前江湖云监控执行 |
| 当前江湖云监控有另一台可用 `local` 主机，且能通过 `ssh_peer` 触发目标主机 | 当前江湖云监控执行 |
| 当前江湖云监控没有可执行主机，已启用“同步主备相关数据”，对端江湖云监控有可执行主机 | 同步给对端江湖云监控执行 |
| 两边都没有可执行主机 | 不下发执行，进入等待执行方或提示无法执行 |

## 10. 防重复执行机制

跨江湖云监控后，最重要的风险是两个江湖云监控或两个插件重复执行同一个切换任务。

需要设置以下保护：

| 保护 | 说明 |
| --- | --- |
| 单关系任务锁 | 同一个 `pair_id` 同一时间只允许一个未完成 `ha_switch_run` |
| 执行方限制 | 只有 `execution_monitor_id` 等于当前 `monitor_id` 的江湖云监控可以下发 `execute_phase` |
| 插件领取限制 | 同一个阶段只能被一个 `claimed_by_host_id` 领取 |
| 领取凭证 | 插件 ack 和日志上报带 `claim_token`，防止旧任务误上报 |
| 日志幂等 | 使用 `event_id` 或 `switch_run_id + origin_host_id + seq` 去重 |
| 冲突状态 | 同步到已有执行中任务时，后到任务进入 `conflict` 或等待人工处理 |

## 11. 页面展示

江湖云监控主备管理页面需要让运维知道数据和任务来自哪里。

| 展示内容 | 说明 |
| --- | --- |
| 状态来源 | 标识主机状态是本地上报，还是从对端江湖云监控同步过来 |
| 最近同步时间 | 显示最近一次成功同步时间 |
| 同步失败原因 | 同步失败时显示错误摘要，方便排查 |
| 同步类型 | 显示当前同步类型，例如“同步主备相关数据” |
| 任务创建方 | 显示切换任务由哪个江湖云监控创建 |
| 任务执行方 | 显示切换任务将由哪个江湖云监控下发执行 |
| 领取主机 | 已领取时显示实际领取任务的插件主机 |

切换确认时，如果任务需要由对端江湖云监控执行，建议明确提示：

```text
该切换任务将在当前江湖云监控创建，并同步到对端江湖云监控执行。
执行方：Mega 江湖云监控
预计领取主机：Dev04B
```

## 12. 同步定时任务

江湖云监控同步由江湖云监控 `task.py` 后台进程定时执行，不需要主备管理插件同时连接两套江湖云监控。

| 项目 | 当前实现 |
| --- | --- |
| 定时任务 | `haMonitorSyncTask()` |
| 执行位置 | `/www/server/jh-monitor/task.py` |
| 执行间隔 | 15 秒 |
| 核心方法 | `ha_api().runMonitorSync()` |
| 日志位置 | `/www/server/jh-monitor/logs/ha_sync/<YYYY-MM>.log` |

任务逻辑：

```text
haMonitorSyncTask
  │
  ├─ 查询 ha_sync_config 中 enabled=1 的同步配置
  ├─ 按 sync_id + sync_type 读取 ha_sync_cursor.last_seq
  ├─ 请求对端 /pub/ha_monitor_sync_pull 拉取增量事件
  ├─ 按 event_type 幂等写入本地 ha_* 表
  ├─ 全部事件应用成功后推进 ha_sync_cursor
  ├─ 尝试调用对端 /pub/ha_monitor_sync_ack
  └─ 写入 last_sync_at / last_error / ha_sync 日志
```

失败处理：

| 场景 | 处理 |
| --- | --- |
| 对端不可达 | 不推进游标，写入 `last_error` 和同步日志 |
| 某条事件应用失败 | 当前批次停止，不推进游标，下次继续从原游标重试 |
| 事件重复拉取 | 查询 `ha_sync_applied`，已应用事件直接跳过 |
| 对端 ack 失败 | 不影响本地已应用结果，只记录后续排查信息 |

## 13. 同步接口签名

江湖云监控之间的同步接口使用独立签名头，和主备插件上报接口区分。

| Header | 说明 |
| --- | --- |
| `X-JHM-Timestamp` | 请求时间戳，超过有效窗口拒绝 |
| `X-JHM-Nonce` | 一次性随机值，已使用 nonce 拒绝 |
| `X-JHM-Body-Hash` | 请求体 SHA256 摘要 |
| `X-JHM-Signature` | 使用同步密钥计算的 HMAC-SHA256 签名 |

签名文本：

```text
timestamp + "\n" + nonce + "\n" + body_hash
```

接收方会按 `sync_id` 查找同步配置；如果两边配置的 `sync_id` 不一致，会在已启用且 `sync_type=ha_management` 的同步配置中按密钥匹配。

## 14. 同步过程示例

### 14.1 A 主机停机，B 侧状态同步回 A

```text
B 插件 report_state 到 B 江湖云监控
  │
  ├─ 上报 B local 正常状态
  └─ 上报 A ssh_peer 失败或最近可见状态
      │
      ▼
B 江湖云监控写入 ha_pair / ha_host_state
      │
      ▼
B 江湖云监控追加 ha_sync_event
      │
      ▼
A 江湖云监控 haMonitorSyncTask 拉取 B 事件
      │
      ▼
A 江湖云监控应用到本地 ha_pair / ha_host_state
      │
      ▼
A 主备管理页面和日报显示同步后的主备状态
```

### 14.2 在 A 江湖云监控发起切换，由 B 执行

```text
运维在 A 江湖云监控点击切换到 B
  │
  ▼
A 创建 ha_switch_run
  │
  ├─ origin_monitor_id = A
  └─ execution_monitor_id = B
      │
      ▼
A 追加 ha_switch_run 同步事件
      │
      ▼
B 江湖云监控定时拉取并应用任务
      │
      ▼
B 插件 poll_monitor 从 B 江湖云监控领取任务
      │
      ▼
B 插件按原有主备切换流程执行 local 或 ssh_peer 阶段
      │
      ▼
B 江湖云监控接收日志和阶段 ack，并追加同步事件
      │
      ▼
A 江湖云监控拉取日志和状态，原切换窗口能看到执行进度
```

### 14.3 两边同时同步同一条事件

```text
A 拉到 event_id=E1
  │
  ├─ ha_sync_applied 没有 E1，执行应用
  └─ 写入 ha_sync_applied(E1)

A 再次拉到 event_id=E1
  │
  └─ 已存在 ha_sync_applied(E1)，直接跳过
```

### 14.4 两边同时创建切换任务

```text
A 已有 pair_id=HA_001 的未完成切换任务
  │
  ▼
A 同步到 B 创建的同一 pair_id 新任务
  │
  ▼
A 检测本地已有未完成任务
  │
  ▼
后到任务标记为 conflict / 不可下发
```

## 15. 上线步骤

1. 确认两套江湖云监控都已更新到包含 `sync-ha-management-between-monitors` 的版本。
2. 分别重启两套江湖云监控：`jhm 1 -y`。
3. 进入 A 江湖云监控“设置 -> 云监控同步”，添加 B 江湖云监控地址，选择“同步主备相关数据”，填写同步密钥并启用。
4. 进入 B 江湖云监控添加 A 江湖云监控地址，使用同一同步密钥并启用。
5. 在两边分别点击“测试连接”，确认能返回对端 `monitor_id` 和名称。
6. 点击“立即同步”或等待 15 秒定时任务执行。
7. 打开两边“主备管理”页面，确认主备关系、主机状态、数据来源、最近同步时间一致。
8. 做一次预上线或测试切换，确认任务创建方、执行方、领取主机和日志同步符合预期。

## 16. 回退步骤

如果同步配置导致状态异常或切换任务流转不符合预期，优先停用同步，不需要删除已有主备管理数据。

1. 进入“设置 -> 云监控同步”，停用对应同步配置。
2. 确认 `/www/server/jh-monitor/logs/ha_sync/<YYYY-MM>.log` 不再出现该 `sync_id` 的新同步记录。
3. 主备管理页面会继续使用本地已有 `ha_*` 表数据，不会继续拉取对端事件。
4. 如果需要彻底清除同步配置，可在设置页面删除配置；删除后会清理该配置对应的同步游标。
5. 如果需要人工清理测试期间产生的主备关系，使用主备管理页面的删除功能逐条删除，不直接删除 SQLite 文件。

## 17. 排障速查

| 问题 | 查看位置 |
| --- | --- |
| 同步任务是否执行 | `/www/server/jh-monitor/logs/ha_sync/<YYYY-MM>.log` |
| 同步配置是否启用 | 设置页面“云监控同步”列表，或 `ha_sync_config.enabled` |
| 最近同步错误 | 设置页面“云监控同步”列表的 `last_error` |
| 游标是否推进 | `ha_sync_cursor.last_seq` |
| 事件是否已应用 | `ha_sync_applied.event_id` |
| 本机生成了哪些事件 | `ha_sync_event` |
| 切换任务由谁执行 | `ha_switch_run.origin_monitor_id` / `execution_monitor_id` |
| 插件是否领取任务 | 插件侧 `/www/server/ha_manager/logs/poll_monitor.log` 和 `cloud_task_launcher.log` |

常用只读查询：

```bash
sqlite3 /www/server/jh-monitor/data/default.db "select sync_id,sync_name,sync_type,peer_monitor_id,enabled,last_sync_at,last_error,status from ha_sync_config;"
sqlite3 /www/server/jh-monitor/data/default.db "select sync_id,sync_type,last_seq,last_event_id,last_sync_at,last_error from ha_sync_cursor;"
sqlite3 /www/server/jh-monitor/data/default.db "select seq,event_id,sync_type,source_monitor_id,event_type,object_key,addtime from ha_sync_event order by id desc limit 20;"
sqlite3 /www/server/jh-monitor/data/default.db "select switch_run_id,pair_id,status,current_phase,origin_monitor_id,execution_monitor_id,claimed_by_host_id,dispatch_reason from ha_switch_run order by id desc limit 20;"
```
